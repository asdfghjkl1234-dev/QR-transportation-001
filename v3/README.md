# 彩色矩陣碼串流傳檔系統 v3

v1 在 [`../`](../)（QR + 噴泉碼，5～15 KB/s），v2 在 [`../v2/`](../v2/)（一幀多碼 + Base45）。
三個版本各自獨立、可以並存 —— v3 不是取代，是換掉「碼」這一層：
不再受 QR 規格限制，自訂一套彩色矩陣碼格式，用顏色（甚至形狀）多載位元。

| 檔案 | 說明 |
|---|---|
| `format.js` | 幀格式：調色盤、版面、標頭、白化、分區規劃、RS 分區編解碼、metadata 分塊 |
| `ecc.js` | GF(256) Reed–Solomon（含抹除解碼）與交錯排列 |
| `render.js` | 把格子內容畫成像素（含形狀層） |
| `detect.js` | 偵測與解碼管線：定位標記 → 幾何校正 → 標頭 → 逐格分類 |
| `pipeline.js` | 「一幀進、一幀出」的封裝，模擬器／測試／實際兩端共用 |
| `simulator.js` | 合成通道模擬器（幾何、模糊、光照、色彩、雜訊、JPEG、撕裂） |
| `simulator.html` | 模擬器的互動介面：逐項失真滑桿、失真強度掃描曲線 |
| `sender.html` | 發送端（預設檔、校準模式、編碼在 worker、刷新週期對齊） |
| `receiver.html` | 接收端（相機、worker 工作池、逐分區疊圖、即時統計與建議） |
| `encoder-worker.js` / `decoder-worker.js` | 兩端的工作執行緒 |
| `benchmark.html` | 各設定的實測成本，以及與 libcimbar 的格式對照 |
| `test.node.mjs` | Node 測試，60 項 |

```sh
npx serve -l 8080 .                   # 在專案根目錄執行

```

## 幀格式

```
┌─────────────────────────────────────────┐
│ ██    ┄┄┄┄┄┄ 時序軌 ┄┄┄┄┄┄┄┄┄┄┄┄    ██ │  ← 四角定位標記（7×7，1:1:3:1:1）
│ ┊  ▓▒░█▓▒░█▓▒░ 上色票條 ░█▓▒░█▓▒░▓  ┊ │  ← 調色盤循環，當局部顏色基準
│ ┊  ▪▫▪▫▪ 標頭（黑白、三重重複）▫▪▫▪  ┊ │  ← 16 B × 3 份 + CRC16
│ ┊  ┌────┬────┬────┬────┐            ┊ │
│ ┊  │ S0 │ S1 │ S2 │ S3 │  資料區     ┊ │  ← 4×3 分區，各自 RS + CRC32
│ ┊  ├────┼────┼────┼────┤  切成分區   ┊ │     每區載一個噴泉碼封包
│ ┊  │ S4 │ S5 │ S6 │ S7 │            ┊ │
│ ┊  ├────┼────┼────┼────┤            ┊ │
│ ┊  │ S8 │ S9 │S10 │S11 │            ┊ │
│ ┊  └────┴────┴────┴────┘            ┊ │
│ ┊  ▓▒░█▓▒░█▓▒░ 下色票條 ░█▓▒░█▓▒░▓  ┊ │
│ ██    ┄┄┄┄┄┄ 時序軌 ┄┄┄┄┄┄┄┄┄┄┄┄    ██ │
└─────────────────────────────────────────┘
      整幀外圈再包 3 格白邊（QUIET_CELLS）
```

版面常數：定位標記 7×7 於四角，分隔線在第 7 列／欄，時序軌在第 8 列／欄，
色票條在第 9 列與倒數第 10 列，標頭緊接在上色票條下方，資料區在其下。
資料區四角各一格「幀序號奇偶」標記，用來偵測捲簾快門造成的撕裂。

### 標頭（16 bytes，三重重複 + 多數決）

| 位移 | 長度 | 內容 |
|---|---|---|
| 0 | 1 | magic |
| 1 | 1 | 版本 |
| 2 | 2 | sessionId |
| 4 | 3 | 幀序號 |
| 7 | 1 | 調色盤等級（4／8／32） |
| 8 | 2 | cols |
| 10 | 2 | rows |
| 12 | 1 | sectorsX |
| 13 | 1 | sectorsY |
| 14 | 2 | CRC16（取 CRC32 低 16 bits） |

### 調色盤

| 等級 | 顏色 | bit/格 | 說明 |
|---|---|---|---|
| C4 | 黑、白、洋紅、綠 | 2 | 洋紅與綠是 CIELAB 的 a\* 軸兩端，黑白是 L\* 軸兩端 —— 兩條互相垂直的長軸 |
| C8 | RGB 立方體八個角 | 3 | 在 RGB 空間裡拉開的最大距離，但在 CIELAB 裡並不等距（黃和白較近） |
| C8+形狀 | 同 C8，再加「反色缺口」位置 | 5 | 實驗性，見下方「第 4 階段」 |

兩兩最小 CIELAB 距離（`format.js` 的 `paletteReport()`，經色偏模型後）：

| | 最小距離 | 最接近的一對 |
|---|---|---|
| C4 | 100.0 | 黑 vs 白 |
| C8 | 49.8 | 青 vs 白 |

## 兩層錯誤更正

```
檔案 ──► LT 噴泉碼（沿用 v2 的 inactivation 解碼器）
          │
          ├─► 封包 ──► 分區 0 ─┐
          ├─► 封包 ──► 分區 1  ├─► 每區：白化 → GF(256) RS → 交錯 → 格子符號
          └─► …              ─┘        （解碼時反向，並用分類信心度做抹除）
```

**內層（每個分區各自獨立）**：資料先做 CRC32 與白化，再切成 ≤255 bytes 的塊
做 GF(256) Reed–Solomon（生成多項式 0x11d，預設冗餘 0.25），最後交錯排列，
讓畫面上相鄰的格子屬於不同的碼字 —— 一道刮痕或一塊反光就不會集中打爆單一碼字。

**抹除解碼**：分類時同時算出信心度（最近距離 ÷ 次近距離），低信心的格子標記為抹除。
RS 對抹除的更正能力是未知錯誤的兩倍（2v + e ≤ nsym），所以這件事很值得做 ——
測試第 7 節裡有一組「60 格誤判」的案例：標記抹除能還原，不標記就解不開。

但**抹除不能亂標**。直覺會以為多標一點比較保險，實測正好相反：

| 信心度門檻 | 標記為抹除的比例 | 分區成功率 | 格子錯誤率 |
|---|---|---|---|
| 0.72 | 0.7% | 92% | 0.38% |
| **0.82**（預設） | 0.3% | 100% | 0.38% |

門檻只影響「標記」，不影響判讀 —— 格子錯誤率完全相同，
但每個多標的抹除都白白吃掉 RS 一個校驗符號的能力。

**外層**：LT 噴泉碼，直接沿用 v2 的 `LTEncoder2` / `LTDecoder2`
（Robust Soliton + 系統區塊 + peeling，卡住時轉 GF(2) 高斯消去）。
一幀的每個分區各載一個封包，所以丟掉任何幀、任何分區都只是少收幾個封包。
實測丟 40% + 亂序仍完整還原，開銷 1.205×（K=308）。

**metadata**（檔名、MIME、檔案大小、區塊大小、整檔 SHA-256）約 150～250 bytes，
一個分區通常只有幾十 bytes 放不下，所以切成數塊，每 15 幀用最前面幾個分區送一輪。
每塊自帶 magic `V3M`、序號、總長與 CRC16，掉了一塊只是繼續等下一輪，不會拼出壞資料。

## 四個階段各自的成果

需求規定嚴格依序開發，每階段通過測試才進下一階段。

### 第 1 階段：幀格式 + 模擬器 + C4（靜態影像解碼）

驗收標準是「中等失真下 C4 格子錯誤 < 1%、C8 < 3%、分區成功率 > 95%」。
中等失真的定義（`simulator.js` 的 `MEDIUM_DISTORTION`）：
留白 10%、旋轉 8°、透視傾斜 0.06/0.04、桶狀畸變 0.06、高斯模糊 σ=0.8、
亮度漸層 22%、反光 0.25、白平衡 (1.06, 1, 0.92)、gamma 1.15、飽和度 0.82、
感光雜訊 6、JPEG 品質 0.75。

實測（100×64、8px 格、4×3 分區、RS 冗餘 0.25）：

| | 格子錯誤率 | 分區成功率 | 幾何殘差 |
|---|---|---|---|
| C4 | 0.00% | 100% | 0.48 px |
| C8 | 0.00% | 100% | — |
| C4（不給網格尺寸提示） | 0.00% | 100% | — |

瀏覽器裡（`simulator.html`，含真實 JPEG 壓縮與色度次取樣）：
C4 格子錯誤 0.13%／分區 100%；C8 0.03%／分區 100%。

### 第 2 階段：真實相機、連續串流

`sender.html` + `receiver.html` 的完整迴圈。無法在這個環境接實體相機，
所以做了兩種等價驗證，兩者都納入測試：

* **Node 端到端**（測試第 12 節）：8 KB 檔案、C8、每幀不同的失真亂數種子、
  隨機丟棄 20% 影格 → 送出 34 幀、丟棄 5 幀、解出 29 幀，
  逐位元組相同、SHA-256 相符，噴泉碼開銷 1.204×，分區成功率 100%。
* **真實瀏覽器端到端**（無頭 Chromium，需 Playwright，未納入 repo）：
  用實際的 `sender.html` + `encoder-worker.js` 產生畫面，抓下畫布、
  經模擬器失真後交給 `pipeline.js` 解碼 → 8 KB／10 幀完成，
  逐位元組相同、SHA-256 相符，每幀解碼 133 ms。

### 第 3 階段：C8 + 信心度抹除解碼

C8 在含 JPEG 色度次取樣的中等失真下，分區成功率一度只有 83%。
根因不在顏色而在幾何：幾何殘差 1.44px 時，取樣點偏離格子中心太多，
顏色被邊界汙染。把殘差壓到 0.48px 之後成功率回到 100%（五幀皆 100%）。

失真強度掃描（100×64、8px 格；格式為「失真值：格子錯誤率／分區成功率」）：

| 失真項 | C4 | C8 |
|---|---|---|
| 高斯模糊 σ | 0:0%/100% 0.8:0%/100% 1.5:0.1%/100% 2.5:12%/解不開 | 0:0%/100% 0.8:0%/100% 1.5:1.7%/92% 2.5:解不開 |
| 感光雜訊 | 0/6/15/30 全部 0%/100% | 同左 |
| 桶狀畸變 | 0/0.06/0.12 → 0%/100%，0.2 → 0.4%/100% | 0/0.06/0.12/0.2 全部 0%/100% |
| 旋轉（度） | 0/8/15/25 全部 0%/100% | 同左 |
| 反光 | 0/0.25 → 0%，0.5 → 0.1%/100%，0.8 → 4.6%/83% | 0.5 → 0.3%/92%，0.8 → 6.1%/83% |
| 亮度漸層 | 0/0.22/0.4/0.6 全部 ≤0.2%/100% | 全部 0%/100% |

### 第 4 階段：效能與實驗性形狀層

**效能。** 需求建議用 WebGL2 做逐格分類，但先量了時間花在哪裡
（2304×1296、18,972 格）：

| 階段 | 加速前 | 加速後 |
|---|---|---|
| 灰階轉換 | 12 ms | 12 ms |
| 縮圖 | — | 9 ms |
| 找定位標記 | 68 ms | 20 ms |
| 幾何校正（建取樣器） | 127 ms **×2** | 57 ms **×1** |
| 逐格分類 | < 10 ms | < 10 ms |
| **整幀解碼** | **276 ms** | **99 ms** |

逐格分類佔不到一成 —— 瓶頸是幾何校正，所以 WebGL2 分類會優化錯的東西。
改成針對瓶頸的三件事，輸出逐格相同：

1. **取樣器不要建兩次**。標頭驗過之後 cols/rows 與候選相同，單應性完全一樣；
   幾何校正只用到定位標記、時序軌、色票條的位置，都與分區怎麼切無關。
2. **定位標記改在縮圖上找**（長邊縮到 1100 px 內，盒狀平均）。
   標記中心只要粗略對，時序軌擬合會修到亞像素級。縮圖會讓中心精度減半，
   代價在 234×129 的 C8（格子僅 7 px）上很明顯（格子錯誤 0.05% → 0.81%、
   分區 100% → 92%），所以挑出四個角之後再在全解析度上精修 —— 只有四個小視窗。
3. **徑向畸變的 k 掃描攤平內層迴圈**：對應點先拆成平坦的 `Float64Array`
   （原本每幀要丟掉兩萬個暫時陣列）；正規方程組只算上三角，
   並利用兩條列各有三個零的結構，一個對應點由 128 次乘法降到 30 次。

   也試過改成「粗掃 + 黃金分割」（約 30 次擬合，再快一倍），結果變差：
   迭代之間是耦合的（這一輪的取樣器決定下一輪追到的軌道），
   殘差對 k 的曲線又不是乾淨的單谷 —— 234×129 的 C8 殘差 0.54→0.76 px、
   格子錯誤 0.06%→0.98%。少算一點卻更不準，不是能接受的交換。

**形狀層（實驗性，`level: 32`）。** 每格除了 C8 的顏色（3 bits），
再在四個角落之一畫一個「反色缺口」，缺口位置帶 2 bits，合計 5 bit/格。
缺口用反色的理由：它必須在「還不知道這格是什麼顏色」時就能被找到，
而 C8 是 RGB 立方體的八個角，任一個角的反色（7−i）正好是對角的那個角，
也就是整個調色盤裡離它最遠的顏色。

結論（1920×1080 螢幕、4×3 分區、RS 冗餘 0.25、每組 8 幀；
**有效酬載 = 每幀酬載 × 平均分區成功率**，整幀解不開的算 0）：

| 拍攝條件 | C8 最佳 | C8+形狀 最佳 | 比值 |
|---|---|---|---|
| 無失真（貼著螢幕、腳架） | 8px → 6,336 B／幀 | **8px → 10,560 B／幀** | **1.67×** |
| 輕微失真 | 8px → 6,336 B／幀 | 10px → 5,767 B／幀 | 0.91× |
| 中等失真（手持） | 8px → 6,336 B／幀 | 10px → 5,450 B／幀 | 0.86× |

也就是說：**貼著螢幕直拍時形狀層是實打實的 1.67 倍；一旦手持，優勢完全消失。**
它必須把格子從 8px 放大到 10px 才穩，格數少掉 1.56 倍，
剛好把多出來的 1.67 倍位元吃回去，還多花約兩倍的解碼時間。

用「有效酬載」而不是「分區全對的幀數」當指標，是因為上層是噴泉碼 ——
掉幾個分區只是少收幾個封包，不是失敗；而這也是唯一能公平比較不同格子大小的指標。

瓶頸不是顏色也不是模糊，是**幾何精度**。顏色取的是格子中心 ±1/3 格的平均，
容得下 0.2 格的取樣偏移；缺口只有 0.24 格寬、中心離格心 0.28 格，完全容不下。
第一版直接照名目位置取樣的結果很能說明問題：

| 格子大小 | 形狀錯誤率（中等失真） |
|---|---|
| 10px | 2.0% |
| 12px | 4.0% |
| 16px | 7.6% |

格子越大反而越糟，而且混淆矩陣顯示是「整批往同一個方向偏」。
那不是解析度不足，是幾何模型在畫面內部還有 0.2～0.3 格的殘差 ——
時序軌只圍住畫面邊界，邊界殘差 0.9px 看起來很好，內部卻偏得多。
對策是把偏移量出來再扣掉：切成 6×4 塊（與分區切法無關）各估一個取樣偏移，
再逐格雙線性內插。評分函式用「1 − 次佳/最佳」的比值而不是絕對差 ——
絕對差有個假的極大值：偏移大到把取樣點推出格子邊界時，取到的是隔壁格子的顏色，
分數看起來超好但判讀全錯。

這也解釋了與 libcimbar 的密度差距（詳見 `benchmark.html`）：
它每格 6 bit，其中 4 bit 來自把整格 8×8 的圖案做樣板比對 ——
用整格的面積換那 4 bit。本專案的缺口只用了約 6% 的格子面積去換 40% 的位元，
面積效率差得多。要真正追上那 2 倍以上的密度差，得走「整格樣板比對」那條路，
而那需要把每一格重新取樣成小圖再和數十個樣板相關（19,000 格 × 64 樣板 × 64 像素），
在 JS 裡跑不動 —— **那才是 WebGL2 真正該用的地方**。

## 幾何校正：為什麼要做到這一步

解碼失敗的原因幾乎都是幾何，而且症狀往往指向錯誤的地方。以下是開發過程中
真正解掉的問題，留在這裡是因為每一個都花了不少時間，而且都不是第一眼想得到的。

**四點單應性不夠。** 用四個定位標記中心配出的單應性，在 6px 格上殘差 4.6px
（18% 的格子錯誤）—— 因為它完全無法描述鏡頭的徑向畸變。
改成沿四條時序軌量出約 200 個黑白交界當對應點，擬合「單應性 + 徑向畸變」，
殘差降到 0.5px、格子錯誤 0%。

**時序軌會「鼓」起來。** 桶狀畸變讓軌道鼓離預測的直線最多快一整格，
照直線取樣會掃到旁邊的資料格，交界被平均掉（實測真值 82 個，照直線只數到 18 個）。
所以追蹤時要連同一個「弓形」參數一起搜尋，而搜尋範圍必須隨軌道長度成長
（100 格約鼓 2 格，234 格會鼓到 5 格以上）。

**弓形的評分不能只看交界數。** 資料格同樣有黑有白，對比一樣是滿的，
交界數又剛好可能碰上預期值 —— 走偏的路徑會贏。加了形狀層之後這個漏洞被放大：
完全無失真的畫面裡，八幀就有一幀的幾何殘差爆到 7.1px、整幀報廢。
真正的時序軌是嚴格一格一換，相鄰交界的間距幾乎都等於一格，桶狀畸變只讓它
緩慢變化；走偏的路徑則忽大忽小。所以把「間距落在中位數 ±40% 內的比例」
加進評分。這一項修好之後，所有失真容忍度都跟著變好（模糊 σ=1.5 的格子錯誤
3.01% → 0.09%）。

**標頭不能放在時序軌圍成的框外。** 一開始放在上帶（兩個定位標記之間），
因為那裡空間大。但時序軌只能校正它自己圍住的範圍，框外只能靠單應性外推，
有桶狀畸變時整條標頭列會被「拱」起來 —— 那是彎曲不是平移，
再怎麼微調取樣位置都補不回來。搬進框內之後問題直接消失。

**標頭的二值化門檻要就地取材。** 反光是局部的：亮斑底下的黑格實測會亮到 176，
而畫面另一端的白格只有 195，單一門檻不管切在哪裡都會錯一大片
（實測 glare=0.5 錯 69/384 位元，三重多數決都救不回來）。
改用 Otsu 更糟 —— 黑格本身已被反光切成「暗黑」與「亮黑」兩群，Otsu 會去切那一刀。
滑動視窗也不行 —— 反光半徑約 26 格，視窗要夠寬才包得到黑白兩色，一寬就又跨出反光範圍。
正解是用「同一個地方的已知黑與白」：上色票條就緊貼在標頭上方，
任何一段連續 8 格裡必定同時有黑和白，取該段的最暗與最亮當基準，中點就是門檻。

**定位標記要濾掉大小不合群的候選。** 畫面一大，資料區裡湊巧形成 1:1:3:1:1 的
位置就變多，實測 150×90 的畫面出現過一個 size=1.4 的假標記（真標記約 6～7）。
它落在 (x+y) 極值上就被當成右下角取走，四點單應性整個歪掉。
中位數要用 n（被幾條掃描線確認）加權 —— 高雜訊下假標記的數量會超過真標記，
純中位數反而把真標記當離群值踢掉（noise=22 就四個角全軍覆沒）；
而真假標記的 n 差距極大（17～19 vs 2～3）。

**全域門檻二值化在大畫面上完全失準。** C4 的調色盤是黑(0)／白(255)／洋紅(105)／綠(150)，
全域平均落在 155 附近，連「綠」都被判成黑。改用 Bradley 局部平均法（積分圖，
每像素 O(1)），亮度漸層、反光、調色盤造成的偏移全部自動吸收。

**沒有白邊就一個標記都找不到。** 定位標記最外圈那一格黑，只要畫面邊緣外面
是深色（桌面、暗牆、模擬器的灰底），就會和背景連成一片，比例檢查直接失敗。
整幀外圈留 3 格白邊。

**尺寸搜尋要有提示與預算。** 桶狀畸變把定位標記往外推、也把它的「格子大小」撐大，
於是「跨距 ÷ 格子大小」算出的欄列數必定偏少（實測 100×64 被估成 94×63）。
搜尋所有候選尺寸時每一組都要重建一次取樣器，實測第一幀要 4.9 秒。
所以接收端解出第一幀之後就一直帶著尺寸提示（降到約 120～250 ms），
並且對提示的尺寸先把 11 種取樣位移都試完再進入清單搜尋 ——
否則清單的快速掃描會先把工作量預算用光，提示的完整模式永遠輪不到
（症狀是幾何殘差明明只有 0.69px 卻回報「畫面品質太差」）。

## 合成通道模擬器

`simulator.html` 是第 1 階段的核心工具，也是後面每一個結論的來源。
每一項失真都有獨立滑桿，套用順序刻意模仿真實成像流程：

```
幾何（透視 + 桶狀畸變）→ 鏡頭模糊 → 場景光照（漸層 + 反光）
→ 相機色彩處理（白平衡 / gamma / 飽和度）→ 感光雜訊 → JPEG → 兩幀混合（撕裂）
```

「掃描失真強度」會對任一項做強度掃描，輸出格子錯誤率／分區成功率／有效吞吐的曲線。

模擬器本身也有兩個必須修對的地方，否則它會騙人：

* **桶狀畸變必須等向**。一開始 x 除以半寬、y 除以半高（各軸分開正規化），
  那等於把徑向畸變做成橢圓形；真實鏡頭是以光軸為中心的圓形，而接收端擬合的
  也是圓形模型。兩者對不上，16:9 的畫面格子錯誤率卡在 20% 以上。
* **「要縮多小才完整入鏡」是個隱式方程式**。透視除法與桶狀畸變都不是線性的
  （半徑減半，畸變效果變四分之一），所以不能拿未縮放的角去量 ——
  那會嚴重高估撐幅，把整張圖縮過頭（8px 的格子在輸出裡只剩 6px，
  定位與取樣精度全部跟著掉）。改成不動點迭代求解。

## 發送端

三個預設檔加一個實驗檔（1920×1080 螢幕、4×3 分區、RS 冗餘 0.25）：

| 預設 | 調色盤 | 格子 | FPS | 網格 | 資料格 | 每幀酬載 | 理論吞吐 |
|---|---|---|---|---|---|---|---|
| 穩定 | C4 | 14px | 8 | 131×71 | 5,307 | 768 B | 6.0 KB/s |
| **標準** | C8 | 10px | 10 | 186×102 | 13,268 | 3,468 B | 33.9 KB/s |
| 極限 | C8 | 8px | 12 | 234×129 | 23,108 | 6,156 B | 72.1 KB/s |
| 腳架（實驗） | C8+形狀 | 8px | 8 | 234×129 | 23,108 | 10,380 B | 81.1 KB/s |

「理論吞吐」= 每幀酬載 × FPS，未計相機端的漏幀與噴泉碼開銷（約 1.2×）。

其他實作細節：

* **格子必須是整數個實體像素**，並關閉所有平滑處理。任何插值都會在格子交界
  產生「兩色的混合色」，而那個混合色很可能剛好落在第三個顏色附近，製造憑空的錯誤。
* **編碼在 worker 裡跑**，預先做好 30 幀放進緩衝區。一幀的編碼實測 10～23 ms，
  放在主執行緒會直接吃掉整個幀預算。
* **幀率對齊螢幕刷新週期**，不是用毫秒計時。用 `requestAnimationFrame`
  數刷新次數，只在刷新邊界換幀 —— 否則換幀會落在螢幕更新的中間，
  相機拍到的就是半幀。
* **校準模式**輪播編號測試圖樣，接收端會算出混淆矩陣並直接建議設定。
* 影片或大檔會提示；可選擇用 WebP 重新編碼縮小。
* 全螢幕時提示關閉夜覽／原彩並把亮度開到最大 —— 那些都會改變螢幕的色彩輸出。

## 接收端

* 後鏡頭 1920×1080、盡量 30fps 以上；相機約束一律用 `ideal`
  （用 `min` 是硬約束，達不到會直接拿不到相機，v1/v2 都踩過），
  並有 1080p60 → 720p30 → 任意相機的降級階梯。
* 定位標記穩定一秒後才用 `applyConstraints` 鎖定對焦／曝光／白平衡；
  要求至少四個標記候選，否則雜訊造成的假標記會讓它亂鎖。
* `requestVideoFrameCallback` 取幀，2～4 個 worker 組成工作池，
  全部忙碌時**直接丟棄影格** —— 排隊只會讓延遲越積越大，
  而噴泉碼本來就不在乎丟掉哪一幀。
* 疊圖逐分區畫框（綠＝CRC 通過、紅＝失敗），統計顯示進度、有效幀率、
  KB/s、格子錯誤率、抹除率、分區失敗率與 ETA；錯誤率高時給具體建議。
* 完成後驗證整檔 SHA-256，並用原始檔名提供下載。

## 與 libcimbar 的對照

`benchmark.html` 的第二節。**沒有做「同一檔案跑兩邊」的吞吐量對比**，
原因是 libcimbar 的解碼器沒有瀏覽器版本 —— 其 README 明確寫著 emscripten/WASM
只編譯了 encoder，decoder 是 C++ 實作、以獨立的 Android app 執行。
沒有可在瀏覽器執行的對照解碼器，硬做出來的數字只會是我們自己的數字換個標籤。
所以改成格式層面的對照，並如實標註哪些數字是對方公布的、哪些是本專案實測的。

| 項目 | v3 標準 | v3 極限 | v3 腳架 | libcimbar（mode B） |
|---|---|---|---|---|
| 資訊來源 | 本機實測 | 本機實測 | 本機實測 | 官方公布規格 |
| 每格像素 | 10×10 | 8×8 | 8×8 | 9×9（圖案 8×8） |
| 每格位元數 | 3（全來自顏色） | 3（全來自顏色） | 5（3 顏色 + 2 形狀） | 6（4 形狀 + 2 顏色） |
| 資料格數 | 13,268 | 23,108 | 23,108 | 12,400 |
| 畫面像素 | 1920×1080 | 1920×1080 | 1920×1080 | 1024×1024 |
| 糾錯後每幀位元組 | 3,468 | 6,156 | 10,380 | 7,500 |
| 資訊密度（bit/像素） | 0.013 | 0.024 | 0.040 | **0.057** |
| 手持可用 | 可用 | 可用 | **不可用** | 官方未分級 |
| 實測持續吞吐 | 未做實機量測 | 未做實機量測 | 未做實機量測 | ~106 KB/s（官方公布） |

差距幾乎全部來自「每格能載幾個 bit」，而那來自「用多少面積去換那些 bit」
（見上方「第 4 階段」）。

另一個交叉印證：本專案量到「顏色是脆弱的維度」——
C8 需要的幾何精度明顯比 C4 高。libcimbar 得到相同結論，
它的 **8 色模式已於 0.6.0 移除**，官方說明是「8-color has always been inconsistent」，
它靠的是形狀不是更多顏色。

libcimbar 為 MPL-2.0 授權，**本專案未使用其任何程式碼**，
上述規格數字引用自其公開文件（README.md / DETAILS.md / PERFORMANCE.md）。

## 已知限制

* **實機吞吐量沒有量過**（沒有實體裝置），上表留空。
  所有數字都來自合成通道模擬器與端到端模擬。
* **形狀層只在貼著螢幕直拍時划算**，手持會整幀垮掉。預設不啟用。
* **模糊是最硬的牆**：8px 格在 σ≈2 以上就開始大量出錯，σ=2.5 只能解出一部分。
  相機對不到焦沒有任何編碼技巧救得回來。
* **反光強度 0.8 以上**分區成功率掉到 83%。反光是局部的，色票條的基準
  只能吃掉緩慢變化的部分。
* **沒有引入 OpenCV.js**。自己實作的定位（1:1:3:1:1 掃描 + Bradley 局部二值化
  + 全解析度精修）與校正（時序軌對應點 + 單應性/徑向畸變聯合擬合）
  已經把中等失真下的幾何殘差壓到 0.5px、格子錯誤 0%，
  不需要為此多載入數 MB 的函式庫。
* **沒有加密**，任何拍得到螢幕的人都收得到同一份資料。
* **狀態全部在記憶體**，依需求沒有使用 `localStorage`。
* 第一幀（不知道網格尺寸）要 1～5 秒；之後帶著尺寸提示約 100～250 ms／幀。
  接收端開 2～4 個 worker，所以實際可處理的幀率大約是單一 worker 的 2～4 倍。
