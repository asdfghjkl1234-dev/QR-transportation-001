# QR 碼串流傳檔系統

用一連串快速閃動的 QR 碼，把檔案從一台裝置的**螢幕**傳到另一台裝置的**相機**。
全程離線、單向、不需要網路、不需要配對、不需要藍牙。

* **`sender.html`** — 選擇檔案，編碼成無限長的 QR 碼串流循環播放
* **`receiver.html`** — 開相機持續掃描，收夠資料就還原檔案並直接顯示／下載
* **`fountain.js`** — 兩端共用的核心邏輯（噴泉碼、封包、CRC、SHA-256）
* **`test.html` / `test.node.mjs`** — 不需要相機的自動化驗收測試

沒有 build 步驟，函式庫從 CDN 載入（並附本地備份）。把整個資料夾丟到任何靜態網站服務即可。

## 為什麼用噴泉碼？

最直覺的做法是「把檔案切成 N 塊，依序播放，播完再從頭來一次」。
問題出在**單向傳輸**：發送端不知道接收端漏了哪幾塊。
假設漏掉第 3 塊和第 700 塊，接收端就得等整整一輪播放結束才補得到，
而且那一輪裡 99% 的畫面都是它早就收過的。實測下來，最後幾塊往往要等好幾分鐘。

**LT 碼（Luby Transform）**把問題整個換掉：發送端不再播「第幾塊」，
而是每一幀都即興產生一個**新的**編碼區塊 —— 隨機挑 d 個來源區塊 XOR 起來。
接收端不在乎收到的是哪幾幀，只要**數量**夠了就能解開全部內容。
漏幀不再需要「等它繞回來」，因為下一幀同樣有用。

```
來源區塊   [0] [1] [2] [3] [4] ...
             \   |   /
              XOR 起來
                 ↓
編碼區塊    ( 0 ⊕ 2 ⊕ 3 )    ← 每一幀都是一個全新的組合
```

### 三個設計重點

**1. 系統區塊優先。**
前 K 幀刻意送度數 1 的「系統區塊」（也就是原始區塊本身，依序送）。
訊號好的時候，第一輪播完就已經 100% 收齊，完全不必付出 LT 碼的解碼開銷。
之後才切換成隨機編碼區塊去補漏掉的洞。

**2. seed 就是全部的約定。**
封包裡**不夾帶**「我 XOR 了哪幾塊」的清單 —— 那會吃掉大量頻寬。
兩端跑同一個確定性 PRNG（mulberry32），只要拿到 4 bytes 的 seed 和 K，
就能各自算出完全相同的索引集合。這是整套系統的一致性基礎，
也是 `fountain.js` 必須被兩端共用的原因。

保留規則：`seed < K` 代表系統區塊，索引就是 seed 本身；`seed >= K` 才是隨機編碼區塊。

**3. Peeling decoder（belief propagation）。**
解碼規則只有一句話：**手上只要出現度數 1 的編碼區塊，它就等於某個來源區塊**。
解出來之後把它從其他區塊裡 XOR 掉，那些區塊的度數就下降，可能又冒出新的度數 1 ——
如此連鎖反應下去。`LTDecoder` 額外維護一份反向索引（`bySource`），
讓每次連鎖只需要碰到真正相關的區塊，而不是每次都掃過全部。

## 封包格式

每一幀是一個二進位封包，轉成 base64 之後塞進 QR 碼的 Byte mode。
（用 base64 而不是直接塞二進位，是因為不少 QR 解碼器會把結果當字串處理，
非 ASCII 的位元組容易在轉碼途中損壞。代價是資料量變成 4/3 倍，換來跨瀏覽器的可靠性。）

| 位移 | 長度 | 欄位 | 說明 |
|---|---|---|---|
| 0 | 2 | magic | 固定 `0x51 0x54`（ASCII `"QT"`） |
| 2 | 1 | version | 協定版本，目前為 1 |
| 3 | 1 | flags | bit0 = 1 表示這是 metadata 幀 |
| 4 | 4 | sessionId | 本次傳輸的隨機識別碼 |
| 8 | 4 | fileSize | 原始檔案總位元組數 |
| 12 | 2 | blockSize | 每個來源區塊的大小 |
| 14 | 4 | K | 來源區塊總數 |
| 18 | 4 | seed | 本幀的 seed（metadata 幀為 0） |
| 22 | n | payload | 資料幀 = 編碼區塊；metadata 幀 = UTF-8 JSON |
| 22+n | 4 | crc32 | 涵蓋前面全部內容 |

多位元組欄位一律 big-endian。標頭共 22 bytes，加上 CRC 共 26 bytes 的固定開銷。

**Metadata 幀**每 20 幀插入一次（含第 0 幀），內容是 JSON：

```json
{ "name": "photo.jpg", "type": "image/jpeg", "sha256": "a3f5…" }
```

接收端要同時「解完所有區塊」**且**「收到 metadata」才算完成 ——
沒有 metadata 就不知道檔名、MIME type，也不知道該比對哪個雜湊。

**CRC32 的作用**：QR 碼本身有糾錯，但仍有極小機率解出錯誤位元組。
一個壞區塊混進 peeling decoder 會污染一大片結果，所以每包都驗 CRC，
對不上就整包丟掉 —— 反正噴泉碼從來不在乎丟掉哪一幀。

## 使用方式

### 快速開始（同一台電腦先試一次）

```sh
npx serve -l 8080 .
```

瀏覽器開 <http://localhost:8080/test.html> 跑完整驗收測試（不需要相機）。
確認全綠之後，再開 `sender.html` 與 `receiver.html`。

> `localhost` 屬於安全來源，相機可以直接使用。要用手機掃，就必須是 **HTTPS**，見下方部署章節。

### 實際傳檔

1. **電腦**開 `sender.html` → 拖入檔案 → 按「開始播放」 → 建議按「全螢幕」
2. **手機**開 `receiver.html` → 按「開啟相機」 → 對準電腦螢幕
3. 進度條跑到 100% 後會自動驗證 SHA-256，並直接顯示圖片／影片與下載按鈕

**拍攝要訣**：讓 QR 碼**填滿相機畫面的一大半**，這比什麼都重要（原因見下一節）。
手機拿穩、對到焦，螢幕亮度調高，避免反光。

## 參數怎麼選

三個參數會互相牽制：**區塊大小**決定 QR 的密度，**FPS** 決定播放速度，
而相機的**解析度與對焦能力**決定了密度的上限。

### 解析度才是真正的瓶頸

QR 碼要掃得動，每個模組（最小的黑白方格）必須佔到**足夠多的相機像素**。
`test.html` 第 4 節會實際模擬這件事（含鏡頭模糊與感光雜訊）：

| 條件 | 每模組所需相機像素 |
|---|---|
| 理想（純縮放，無模糊雜訊） | 2 px |
| 貼近真實（模糊 0.8px + 雜訊 ±18） | **3 px** |

換算成實際需求（含四周 4 個模組的 quiet zone）：

| 區塊大小 | QR 版本（ECC L） | 模組數 | 連 quiet zone | 相機中需佔 | 1080p 畫面高度占比 |
|---|---|---|---|---|---|
| 200 B | v11 | 61 | 69 | ~207 px | 19% |
| 600 B | v20 | 97 | 105 | ~315 px | 29% |
| 900 B | v25 | 117 | 125 | ~375 px | 35% |
| 1200 B | v30 | 137 | 145 | ~435 px | 40% |

這就是為什麼「讓 QR 填滿畫面」比調高 FPS 有效得多 ——
把 QR 從畫面的 30% 拉到 60%，等於解析度直接翻倍。

### 建議組合

| 情境 | 區塊大小 | FPS | ECC | 說明 |
|---|---|---|---|---|
| **通用預設** | 600 B | 10 | L | 大多數手機的甜蜜點 |
| 手機較舊／光線不佳 | 400 B | 8 | M | QR 更稀疏、更耐髒污與反光 |
| 高階手機 + 貼近拍攝 | 900 B | 12 | L | 需要穩定的手持與良好對焦 |
| 只想確保能傳到 | 200 B | 6 | M | 最保險，但很慢 |

**糾錯等級**：預設 **L**（7%）。QR 顯示在螢幕上，本來就沒有印刷品的髒污磨損問題，
把冗餘度留給資料更划算。只有在反光嚴重、或螢幕有刮痕保護貼時才值得換 M ——
換 M 大約要多付 2～4 個 QR 版本的密度代價。

**FPS 不是越高越好**。真正的限制是接收端每秒能解幾幀（見下方實測），
播得比對方掃得動還快，只是讓更多幀直接被漏掉而已。
不過噴泉碼的好處是：**漏幀不會讓傳輸失敗，只會讓它變慢**。

## 部署

手機瀏覽器只在 **HTTPS 或 localhost** 下才允許存取相機。以下兩種方式擇一。

### 方式一：靜態網站服務（推薦）

整個專案就是純靜態檔案，沒有 build 步驟。

**Vercel**

```sh
npm i -g vercel
vercel deploy --prod
```

（專案根目錄不需要任何設定檔；Vercel 會直接把資料夾當靜態站台發布。）

**GitHub Pages**

1. 把整個資料夾推上 GitHub
2. Repository → Settings → Pages
3. Source 選 **Deploy from a branch**，分支選 `main`、資料夾選 `/ (root)`
4. 等一兩分鐘，網址會是 `https://<帳號>.github.io/<專案名>/sender.html`

> **注意**：`fountain.js` 是 ES module，必須透過 HTTP(S) 載入。
> 直接用 `file://` 開啟 HTML 會因為瀏覽器的 CORS 限制而失敗 —— 一定要起一個伺服器。

### 方式二：本機開發 + HTTPS 通道

本機起服務：

```sh
npx serve -l 8080 .
```

再用 [cloudflared](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/)
開一條臨時 HTTPS 通道（不需要帳號）：

```sh
cloudflared tunnel --url http://localhost:8080
```

它會印出一個 `https://<隨機字串>.trycloudflare.com` 網址，
手機直接開那個網址底下的 `receiver.html` 即可。

> 電腦端的 `sender.html` 用 `http://localhost:8080` 開就好 ——
> **發送端不需要相機權限**，只有接收端需要 HTTPS。

其他等效選擇：`ngrok http 8080`、`tailscale funnel 8080`，或自己簽憑證。

## 專案結構

```
fountain.js      共用核心：PRNG、CRC32、SHA-256、Robust Soliton、封包、LT 編解碼器
sender.html      發送端：切塊、產生 QR、Canvas 播放
receiver.html    接收端：相機、QR 解碼、peeling 解碼、驗證與還原
test.html        瀏覽器驗收測試（含真實的 QR 編碼→解碼往返）
test.node.mjs    Node 測試（48 項，純邏輯層）
vendor/          第三方函式庫的離線備份（CDN 連不上時自動啟用）
```

### 第三方函式庫

| 用途 | 套件 | 版本 | 授權 |
|---|---|---|---|
| QR 編碼（發送端） | [qrcode-generator](https://www.npmjs.com/package/qrcode-generator) | 1.4.4 | MIT |
| QR 解碼（接收端退路） | [jsQR](https://www.npmjs.com/package/jsqr) | 1.4.0 | Apache-2.0 |

兩者都是**先試 CDN、失敗才用 `vendor/` 的本地備份**，所以完全沒有網路也能運作。

接收端優先使用瀏覽器**原生的 `BarcodeDetector` API**（Android Chrome 支援良好，速度快得多），
只有在不支援時才退回 jsQR —— 而且是放在 Web Worker 裡跑，避免純 JS 解碼卡住畫面更新。

## 測試

```sh
npm test          # Node：48 項，涵蓋標準測試向量、CRC 防護、丟幀亂序還原
```

瀏覽器測試開 `test.html`，它會實際執行：
**切塊 → 編碼 → 封包 → base64 → 真的畫成 QR → 真的用 jsQR 解回來 → peeling 解碼 → SHA-256 驗證**，
並在過程中丟掉 30% 的幀、把順序完全打亂。

`test.node.mjs` 中比較值得一提的幾項：

* **SHA-256／CRC32 對標準測試向量**（NIST 向量、`CRC32("123456789") == 0xCBF43926`）
* **逐位元組竄改**：把封包的每一個位元組都翻一次，確認 CRC32 全數攔下
* **丟幀率 0%～90%** 都能還原 —— 噴泉碼的表現是「變慢」，而不是「失敗」
* **解碼開銷統計**：見下一節

### 關於「K × 1.05～1.2」這個目標

原始需求寫的是「收到約 K × 1.05～1.2 個不同區塊就能還原」。
實測結果是：**這個目標在 K 夠大時成立，K 小的時候不成立** ——
因為 LT 碼的效率是**漸進的**，K 越大越接近理論值。

刻意跳過系統區塊、只用隨機編碼區塊解碼（最壞情況）的實測：

| K | 平均開銷 | 最差開銷 |
|---|---|---|
| 50 | 1.42× | 1.72× |
| 200 | 1.26× | 1.45× |
| 350 | 1.24× | 1.62× |
| 900 | 1.13× | 1.19× |
| 2000 | **1.12×** | **1.16×** |

實務上影響很小，原因有兩個：

1. **K 小的時候，絕對幀數也小**。K=50 多付 70% 是多送 35 幀，在 10 FPS 下只是 3.5 秒。
2. **真實情況有系統區塊**。訊號好時第一輪就收完（實測 1.00× K），
   根本不會走到隨機編碼區塊那條路。

真正會遇到大 K 的是實際檔案：200 KB／600 B 區塊 = K 342，
1 MB = K 1748，此時開銷就落在 1.1～1.2× 的區間內。

參數 `c = 0.03`、`δ = 0.05`（`fountain.js` 的 `RS_C` / `RS_DELTA`）是掃描過
c ∈ [0.01, 0.2] × δ ∈ [0.001, 0.5] 的網格之後挑的：
在大 K 時表現最好，而在真實情境（含系統區塊）下各組參數差異其實很小。

## 已知限制

* **這是為了好玩與離線應急而做的**。要傳大檔案，AirDrop／隨身碟／區域網路都快上好幾個數量級。
* **5 MB 以上會很久**。發送端會跳警告。影片建議先壓到很低的位元率，圖片可以勾選內建的 JPEG 縮圖壓縮。
* **沒有加密**。任何能拍到螢幕的人都能收到同一份資料。要保密請自己先加密再傳。
* **iOS Safari 沒有 `BarcodeDetector`**，會退回 jsQR，解碼速度明顯較慢，建議把 FPS 調低。
* **檔案大小上限 4 GB**（標頭的 `fileSize` 是 4 bytes），實務上遠遠碰不到。
* **狀態全部在記憶體**，依需求沒有使用 `localStorage`。重新整理頁面就得從頭來過。
