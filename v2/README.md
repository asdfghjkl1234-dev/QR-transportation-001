# QR 碼串流傳檔系統 v2（高速版）

v1 在 [`../`](../)，兩個版本各自獨立、可以並存 —— v2 不是取代，是另一條路線。

v1 的實際吞吐約 5～15 KB/s。v2 的目標是 30～80 KB/s，做法是四項互相獨立的加速，
每一項都可以單獨關掉，方便逐項驗證效果。

| 檔案 | 說明 |
|---|---|
| `fountain2.js` | v2 核心：Base45、v2 封包、QR 容量推算、LT 編碼器、inactivation 解碼器 |
| `sender.html` | 發送端（一幀多碼、編碼在 worker、刷新週期對齊） |
| `receiver.html` | 接收端（多碼解碼、worker 工作池、畫框、即時統計） |
| `encoder-worker.js` | 發送端編碼工作執行緒 |
| `decoder-worker.js` | 接收端 zxing-wasm 解碼工作執行緒 |
| `test.html` | 瀏覽器驗收測試（真實 QR 編解碼往返） |
| `test.node.mjs` | Node 測試，65 項 |
| `vendor/` | qrcode-generator 與 zxing-wasm 的本地副本 |

## 四項加速，各自的實測效果

### 一、一幀多碼（貢獻最大）

一幀不只放一個 QR，而是切成網格同時顯示多個。每個碼都是**完整獨立的封包**
（各自帶 seed 與 CRC），格與格之間留 8 個模組寬的白邊（每格各留 4 個）當靜區，
所以漏掉其中一格完全不影響其他格。

接收端一次解出畫面中所有的碼：

* 原生 `BarcodeDetector.detect()` 本來就回傳陣列，天生支援
* zxing-wasm 的 `readBarcodes()` 設定 `maxNumberOfSymbols` 為網格數量

**實測**（zxing-wasm 掃描 1920×1080 畫面，網格佔畫面高度 90%）：

| 網格 | QR 版本 | 每幀耗時 | 解碼幀率上限 | 全數解出 |
|---|---|---|---|---|
| 1×1 | v20 | 21 ms | 46.9 FPS | ✓ |
| 2×2 | v15 | 25 ms | 40.7 FPS | ✓ |
| 3×2 | v15 | 24 ms | 41.4 FPS | ✓ |
| 3×3 | v15 | 34 ms | 29.2 FPS | ✓ |
| 3×3 | v20 | 33 ms | 30.2 FPS | ✓ |

值得注意的是**解一個碼和解九個碼的成本幾乎一樣**（21 ms vs 33 ms）——
定位與二值化是整張畫面一起做的，多找幾個碼只多花一點點。
所以一幀多碼幾乎是「免費」的倍數成長，這也是它效果最好的原因。

### 二、Base45 + QR 英數模式

v1 把封包轉成 base64 再用 QR 的**位元組模式**：每個字元佔 8 bits 卻只帶 6 bits 資料，效率 75%。

v2 改用 **Base45（RFC 9285）+ QR 英數模式**：英數模式每 2 個字元用 11 bits 編碼，
而 Base45 每 3 個字元帶 2 bytes，等於 16.5 bits 承載 16 bits，效率 **97%**。

Base45 的 45 個字元 `0-9 A-Z 空格 $%*+-./:` 剛好就是 QR 英數模式的合法字元集 ——
這不是巧合，RFC 9285 正是為此設計的。測試裡有一項專門驗證這兩個字元集完全相同。

**實測每個 QR 能裝的區塊大小**（糾錯 L，已扣掉封包標頭）：

| QR 版本 | 英數字元數 | v2 區塊大小 | v1 同版本（base64） | 提升 |
|---|---|---|---|---|
| v10 | 395 | 248 B | 175 B | +42% |
| v15 | 758 | **490 B** | 364 B | +35% |
| v20 | 1249 | 817 B | 616 B | +33% |
| v25 | 1853 | 1220 B | 928 B | +31% |
| v30 | 2520 | 1665 B | 1273 B | +31% |

順帶一提，這也解決了 v1 的一個隱憂：`BarcodeDetector` 只回傳字串（`rawValue`），
位元組模式的二進位內容經過字串轉換可能受損；Base45 是純 ASCII，無損還原。

### 三、精簡封包格式

v1 每個封包固定花 26 bytes 在標頭上。v2 把「每一幀都一樣」的欄位
（檔案大小、區塊大小）搬到 metadata 幀，資料幀只留必要的：

| 位移 | 長度 | 欄位 |
|---|---|---|
| 0 | 1 | magic `0x51` |
| 1 | 1 | bit0-3 版本、bit4 metadata 旗標、bit5-6 顏色通道 |
| 2 | 2 | sessionId |
| 4 | 3 | K（來源區塊數，最多 16,777,215） |
| 7 | 4 | seed |
| 11 | n | payload |
| 11+n | 4 | CRC32 |

**固定開銷 26 → 15 bytes。** metadata 幀每 15 個資料幀插一次，
內容是 JSON：檔名、MIME type、檔案大小、區塊大小、整檔 SHA-256。
接收端在收到 metadata 之前會先把資料幀暫存起來（因為精簡標頭不再攜帶區塊大小）。

### 四、Inactivation decoding

v1 用純 peeling（belief propagation）：只有出現「度數 1」的方程式才有進展，
一旦剩下的方程式度數都 ≥ 2 就卡死，只能等下一個剛好接得上的封包。

v2 在 peeling 卡住時，把剩下的方程式當成 **GF(2) 上的線性方程組直接用高斯消去法解**。
GF(2) 的加法就是 XOR，所以係數矩陣可以壓成 `Uint32Array` 位元圖，一次處理 32 個未知數；
payload 也用 `Uint32Array` 檢視做 XOR。

**實測解碼開銷**（只餵隨機編碼區塊，最能反映解碼器本身的效率）：

| K | v2 平均開銷 | 比理論下限多付 | v1（純 peeling） |
|---|---|---|---|
| 50 | 1.076× | 3.8 個封包 | 1.42× |
| 100 | 1.030× | 3.0 個封包 | — |
| 200 | 1.018× | 3.6 個封包 | 1.26× |
| 500 | **1.004×** | 2.1 個封包 | — |
| 1000 | **1.005×** | 4.6 個封包 | 1.13× |
| 2000 | **1.001×** | 2.6 個封包 | 1.12× |

理論下限是 1.000×（要解出 K 個未知數，至少需要 K 個線性獨立的方程式）。
重點是：**多付的封包數是個幾乎固定的常數（2～5 個），不隨 K 成長**。
K 很小時比值看起來偏高，只是因為常數除以很小的分母。

> **這個解碼器在資訊論上是最佳的。**
> 我另外寫了一個增量計算 GF(2) 秩的追蹤器，量測「已收到的方程式什麼時候達到滿秩 K」，
> 也就是數學上最早可能解完的時刻。結果解碼器**每一次都剛好在那一刻完成，落後 0 個封包**。
> 換句話說，剩下的開銷完全來自編碼端產生的方程式彼此線性相依，
> 不是解碼器沒把資訊榨乾。

## 一個違反直覺的實測結果：系統區塊在 v2 反而會拖慢

v1 的設計是「前 K 幀先依序送原始區塊（系統區塊）」，理由很充分：
純 peeling 解碼器需要 1.1～1.2 倍才解得開，先送一輪原始區塊的話，
訊號好時第一輪就收完，完全不必付解碼開銷。需求文件也要求 v2 保留這個設計。

但 v2 的 inactivation 解碼器讓隨機編碼區塊的開銷降到 **1.01 倍**，
這時系統區塊的缺點就浮上來了：

**實測**（200 KB 檔案、依序抵達、數字是「收到的區塊數 ÷ K」，越低越好）：

| 丟幀率 | 系統區塊優先 | 全程隨機編碼 |
|---|---|---|
| 0% | 1.005× | 1.011× |
| 10% | 1.329× | **1.009×** |
| 20% | 1.350× | **1.010×** |
| 40% | 1.269× | **1.011×** |
| 60% | 1.135× | **1.008×** |

只有**完全不漏幀**時兩者才打平，只要開始漏幀，系統區塊就明顯落後。

原因：漏掉的系統區塊要靠後續的隨機編碼區塊來補，但那些區塊的度數分布
（Robust Soliton）是針對**整個 K** 設計的。化簡掉已知區塊之後，
有相當比例會塌成度數 0（完全沒有新資訊）—— 光是度數 2 就佔了 soliton 一半的機率質量，
其中約 36% 會塌掉。這些就是線性相依的來源。

**目前的處理**：預設維持開啟（沿用 v1 設計、也符合需求文件），
但在發送端 UI 上做成可以關閉的開關，並附上說明。
**實際使用時如果環境會漏幀（正常情況都會），建議關掉它。**

## 吞吐量

### 理論值

```
吞吐 = 區塊大小 × 一幀的碼數 × FPS
```

| 預設 | 網格 | 版本 | FPS | 區塊 | 一幀資料 | 理論吞吐 |
|---|---|---|---|---|---|---|
| 穩定 | 1×1 | v20 | 10 | 817 B | 817 B | 8.0 KB/s |
| **快速**（預設） | 2×2 | v15 | 12 | 490 B | 1960 B | **23.0 KB/s** |
| 極速 | 3×3 | v15 | 15 | 490 B | 4410 B | **64.6 KB/s** |
| 極速+ | 3×3 | v20 | 15 | 817 B | 7353 B | **107.7 KB/s** |

v1 在 600 B 區塊、10 FPS 下是 5.9 KB/s。所以「快速」約為 v1 的 **4 倍**，
「極速」約 **11 倍**，達到 30～80 KB/s 的目標。

要注意「快速」預設只有 23 KB/s，還沒進到目標區間 ——
**想達到 30 KB/s 以上必須用 3×2 以上的網格**。這是刻意的取捨：
預設值優先考慮「拿起手機就能掃到」，極速檔才是衝吞吐用的。

## RGB 三通道模式（實驗性，預設關閉）

每一格同時放 3 個碼，分別編進 R、G、B 通道（黑=0、白=255），理論吞吐 ×3。
接收端把影格拆成三張灰階圖，各自用**自適應二值化**（Bradley 局部平均法，
以積分圖做到每像素 O(1)）之後分別解碼。每 30 幀插入一次黑白棋盤校準幀，
讓接收端量出各通道的白點與黑點數值來估算色偏。

**在 canvas 上直接拆通道是可行的**，測試裡三個通道都能 100% 還原，
一幀承載黑白模式的 3 倍資料量。

**但這不代表實機可行。** 手機相機幾乎都會做**色度次取樣**
（4:2:0 —— 顏色資訊的解析度只有亮度的一半），而 QR 的模組邊緣正是高頻訊號，
很可能在進入 JavaScript 之前就已經被相機的影像處理管線抹掉了。
再加上白平衡會動態改變三個通道的相對增益。

我**沒有辦法驗證這個功能在真實相機下是否可用**。UI 上標示為實驗性，
如果打開後 CRC 失敗率很高，就是被色度次取樣吃掉了，請切回黑白模式。

## RaptorQ（RFC 6330）：沒有做

需求說「如果能找到可用且仍在維護的 RaptorQ WASM 套件就做成選項，找不到就不要硬做」。

npm 上的 `raptorq` 套件最後發布於 2023 年，`package.json` 裡沒有 `main` 欄位，
指向的是 Rust crate 的儲存庫（cberner/raptorq），不是能直接在瀏覽器用的 WASM 建置。
沒有找到其他仍在維護、可直接引入的瀏覽器版本。

**所以沒有做，也不需要做**：RaptorQ 的主要賣點就是接近 1.0 的解碼開銷，
而 v2 的 inactivation 解碼器實測已經是 1.001～1.005×，並且證實在資訊論上是最佳的
（見上方）。剩下的開銷來自編碼端的線性相依，換成 RaptorQ 的前置碼（precode）確實會改善，
但那是幾個百分點的差距，遠不如「一幀多碼」帶來的數倍提升重要。

## 其他實作細節

**編碼全部在 Web Worker**。產生一個 v20 的 QR 要十幾毫秒，一幀 4 個碼就是 60 ms，
放在主執行緒根本撐不住 12 FPS。所以 worker 負責「產生封包 → 編 QR → 合成整幀」，
並**預先做好 60 幀**放進緩衝區；主執行緒只負責貼圖。

worker 輸出的 `ImageBitmap` 一律是「1 像素 = 1 個 QR 模組」的原始尺寸，
主執行緒再用**整數倍**放大並關閉 `imageSmoothing`。非整數倍會讓模組邊界
落在半個像素上，相機拍起來就糊了。

**以刷新週期計時，而不是毫秒**。頁面載入時先量測螢幕更新率（取 40 次 rAF 間隔的中位數，
再吸附到常見的 60/75/90/120/144/165/240 Hz），然後每張圖固定停留
`round(更新率 / 目標FPS)` 個刷新週期。用時間換圖的話，某些幀會剛好跨越兩次刷新、
某些只顯示一次，畫面長短不一，相機更容易拍到撕裂的畫面；對齊刷新週期之後每張圖
的曝光時間完全一致。

**接收端的 worker 工作池**。依 `navigator.hardwareConcurrency` 開 2～4 個 worker。
影格用 `createImageBitmap` 轉移（不複製像素）給閒置的 worker；
**全部忙碌時直接丟棄該影格，絕不排隊** —— 排隊只會讓延遲越積越大，
而噴泉碼本來就不在乎丟掉哪一幀。

**鎖定對焦與曝光**。相機的自動對焦會不斷來回搜尋，每次搜尋期間畫面都是糊的。
`applyConstraints` 支援時會設成 `continuous`（比 `manual` 實際，多數裝置不支援 manual）。

**相機約束一律用 `ideal`**。開發過程中踩到一個坑：原本寫 `frameRate: { min: 30 }`，
結果在不支援 30fps 的裝置上直接丟 `OverconstrainedError`，變成「完全沒有相機」
而不是「幀率低一點的相機」。現在改成由嚴到寬依序嘗試 1080p60 → 720p30 → 只要有相機就好。


* 測試：<http://localhost:8080/v2/test.html>
* 發送端：<http://localhost:8080/v2/sender.html>
* 接收端：<http://localhost:8080/v2/receiver.html>（手機需要 HTTPS）

```sh

```

部署方式與 v1 相同（Vercel / GitHub Pages / cloudflared 通道），
詳見 [根目錄的 README](../README.md#部署)。手機相機只能在 HTTPS 或 localhost 下使用。

### 第三方函式庫

| 用途 | 套件 | 版本 | 授權 |
|---|---|---|---|
| QR 編碼 | [qrcode-generator](https://www.npmjs.com/package/qrcode-generator) | 1.4.4 | MIT |
| QR 解碼（多碼） | [zxing-wasm](https://www.npmjs.com/package/zxing-wasm) | 3.1.3 | MIT |

兩者都放在 `vendor/` 直接引用，沒有走 CDN。原因：

* **qrcode-generator**：v2 的編碼在 ES module 型態的 worker 裡跑，
  而 module worker 不能用 `importScripts()`，只能 `import`。
  原始套件是 UMD/全域變數形式，所以在檔尾補了一行 `export default qrcode;`
  （上方原始碼一字未改）。
* **zxing-wasm**：需要搭配 1.1 MB 的 `.wasm`，且 `reader/index.js` 會
  `import "../share.js"`，必須保留套件原本的目錄結構。放本地才能確保離線可用、
  版本固定。

兩個版本的 API 都已實際驗證過：`qrcode(version, ecc).addData(text, 'Alphanumeric')`
可用，`readBarcodes(imageData, { maxNumberOfSymbols })` 能一次回傳多個結果並附
四角座標（接收端用來畫框）。

→ 真的用 zxing-wasm 一次解出全部 → inactivation 解碼 → SHA-256 驗證**，

## 已知限制

* **實機吞吐量與 CRC 失敗率沒有量過**（沒有實體裝置），README 留了空表格。
* **RGB 模式未經實機驗證**，很可能被相機的色度次取樣打敗。
* **沒有加密**，任何拍得到螢幕的人都收得到同一份資料。
* **極速檔需要大螢幕**，而且手機最好固定在支架上 —— 3×3 網格的每個碼只有畫面的 1/9。
* 高斯消去的成本是 O(n²×(n/32+區塊/4))，未知數超過 2000 就先跳過等 peeling 把 n 壓下來，
  避免在主執行緒上凍住畫面。
* **狀態全部在記憶體**，依需求沒有使用 `localStorage`。
